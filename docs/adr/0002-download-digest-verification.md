# 0002 — 用 GitHub digest 做下载完整性校验，默认开启并阻断

- 状态：已接受
- 日期：本会话
- 相关：`Services/Net/DownloadIntegrityGuard.cs`

## 背景

引入第三方镜像后，下载链路上多了一个能看到并能改写字节的中间人。项目此前没有任何发布者签名校验，只有"本地文件 hash 与远端 hash 是否相同决定要不要更新"的比较（`ModInstallService`）——这既防不住篡改，还会因为镜像给了错文件而触发**无限更新循环**。

## 考虑过的选项

1. 不校验：镜像只是"换个搬运工"，与现状风险相比没有实质变化。
2. 只校验数据文件（`manifest.json` 等），DLL 不校验。
3. 全量校验所有下载内容。
4. 只校验"能拿到权威摘要"的内容，拿不到就降级为长度/文件头检查。

## 决定

选 **4**，并且**默认开启**：

- release 资产：比对 `api.github.com` 公布的 `digest`（实测可用，字段形如 `sha256:…`）。
- 数据文件：比对 `contents` API 的 blob sha（本地按 `sha1("blob {len}\0" + bytes)` 计算）。
- 拿不到权威摘要的地址：降级为 `Content-Length` 比对 + 文件头检查（`.dll` 需 MZ、`.7z` 需签名），**不阻断**。
- 校验失败：丢弃产物 → 标记该来源不可信 → 用直连重下 → 仍失败则中止并提示用户。
- 摘要查询带 24 小时磁盘缓存，并复用既有 ETag 机制；无 GitHub token（限流 60/h）时降低校验频率，但不阻断安装。

## 后果

**好处**：镜像无法静默替换 DLL；`ModInstallService` 的更新循环问题被顺带治好；用户可以在设置里关掉它，知情选择。

**代价**：每次下载后可能多一次 API 调用（有缓存与限流兜底）；unauthenticated 情况下限流紧张，需要降级策略。

**为什么默认开而不默认关**：这个应用的产物是写进用户游戏目录的 DLL，静默篡改的后果是用户机器被控。选择"默认安全、可以关掉"，而不是"默认宽松、可以打开"。
